## Running OpenCompletion

### Environment Setup
- Use `vars.sh` to set up environment variables
- Required: MODEL_ENDPOINT_x and MODEL_API_KEY_x variables for machine learning models
- Run with: `source vars.sh && python app.py`
- **NEVER cat or grep vars.sh** - it contains API keys and secrets

### Makefile Commands
- `make venv` - Create virtual environment and install dependencies from our hash-locked files, then `venv_prune.py` uninstalls whatever no lock names (`pip install` never removes a dropped dependency; pip, setuptools & wheel stay)
- `make init-db` - Create our database, or bring an existing one up to date (`init_db.py` → `db_migrate.bring_up_to_date`, the same call `python app.py` makes at startup)
- `make upgrade-db` - Apply migrations to an existing database (`FLASK_APP=app.py venv/bin/flask db upgrade`, needs vars.sh). It & `init-db` set `OPENCOMPLETION_SKIP_MODEL_MAP=1`, so no model endpoint is asked for its list (a dead one can't stall them); the app lists each endpoint once, no retries
- `make test` - Unit, integration, functional tests & YAML validation (no network)
- `make test-ui` - Page contract & mobile layouts in headless Chromium
- `make lint` - black --check & flake8 (syntax, undefined & unused names)
- `make ci` - lint + test: what GitHub Actions checks, one stage after another (there each stage is its own parallel job, `functional` in two halves: `make test-functional-a-m` & `-n-z`)
- `make backfill-titles` - Title every untitled room holding a conversation (network: a chat model)
- `make backfill-blobs` - Move base64 images kept inside messages (old DALL-E & vision replies) into our blob store (no network)
- `make chain-check` - Verify every room's hash chain, deleted rooms' included (`app.py --chain-check`, needs vars.sh): the line rule & links, checkpoints, & live messages against their chained digests; fails on any break
- `make harvest` - Our tool calls' repair evidence (`app.py --harvest [DIR]`, `harvest.py`, needs vars.sh, no network): reads every reply's `tool_trail` (raw arguments) & every room chain's `tool` events (status, error & repair marks via `tools.loop.repair_marks`, never arguments; deleted rooms included) into `instance/harvest/repair/{repaired,unparsed,errors}.jsonl` (owner-only, rewritten each run), one row a call (errors from chains, matched to trails by result sha256; repairs from trails, a deleted room's from its chain with `raw: null`), & reports what repairs save, which unparsed calls today's `toolcall_repair` now reads & the shapes of the rest; the lanes match uncloseai-cli's repair lane
- `make coverage-check` - Fail below our 82% coverage floor (CI measures it in four parallel parts, `make coverage-unit`, `-integration`, `-functional-a-m` & `-functional-n-z`, then job `coverage` adds them up with `make coverage-combine`: same tests, same floor; `.coveragerc` counts tools/, activity_engine, blob_store, chain, fade, classifier & the game modules too); raise it as tests land, never lower it

### Network Infrastructure

- OpenCompletion uses Caddy for web server (not nginx)
- Multi-layer proxy architecture for accessing machine learning models
- Network troubleshooting notes are kept privately, not in this repo

## OpenCompletion Architecture

### Backend Structure
- `app.py`: our Flask app, chat itself (`/chat/<room>`, Socket.IO events, model streaming, title helpers) & the model map
- `routes/`: HTTP blueprints registered by `routes.register(app, ...)`: `pages.py` (home, sign in, profile, style guide), `accounts.py` (email-code sign in, names), `rooms.py` (the Rooms page: filter & message search `?q=`, old `/search` redirects; rooms API, downloads, `room_access_denied`), `code.py` (unsandbox proxy, fix-code, artifact names), `status.py` (`/version`: running commit, its date & process start, `OPENCOMPLETION_GIT_COMMIT` for a deploy without .git; `/health`: 200 with our database answering `SELECT 1`, else 503; `/health/models`: 200 while our model map lists a chat model, else 503 (`models`: ok, no models, never built), with counts & the map's age only (`app.model_map_status` via DEPS: endpoints configured & listing, models, chat models; never a URL, a key or a model id), read from memory & nudging a stale map to rebuild as `/models` does (`refresh_stale_model_map`); none calls a model nor says why)
- `bedrock.py`: AWS Bedrock's Claude models (only ids named in `OPENCOMPLETION_BEDROCK_MODELS`, comma separated, unset = none: a model id comes from whoever posts, & Bedrock is asked under our AWS credentials; `chat_claude` in app.py), no Flask, database or socket: it turns `reply_history`'s turns into Bedrock's messages (words only, roles never repeated) & yields the answer's words; `chat_claude` runs them through a `ReplyStream` (`emit_content`, `finish`, `fail`), so its Message, chunks, completion & chain line are chat_gpt's. No tools, thinking, steering or resume. boto3 is imported only when asked; credentials & region are AWS's own (`--profile`, `AWS_REGION`, else us-west-2), never in vars.sh. Never run against AWS in tests (`tests/unit/test_bedrock.py` replaces boto3)
- `activity_engine.py`: our one activity engine (a learner's answer to a step, the walk to the next question), no Flask, database or socket: `activity.py`'s `RoomIO` runs it in a chat room (ActivityState, messages, emits) & `research/guarded_ai.py`'s `TerminalIO` in a terminal (MemoryState, print & input), so a fix lands in both. Step scripts get `metadata` with `user_response` in it, read/write (SPEC.yaml); their writes & `script_result.metadata` are kept. `activity_grading.py` (pure, shared the same way) is unyaml's grading (unhomeschool's `lessons/SCHEMA.md`, v0.5.1): `bucket_criteria` & `required_elements` written into every grader's instructions (missing an element = partial, never correct); a clarifying bucket (`asking_clarifying_questions`) on every question step, never an attempt, with a built-in transition unless the step has its own (`allow_clarifying_questions: false` on the activity or a step turns it off, for games); multiple choice (`question_type: multiple_choice`, `choices` {id, text}, `answer`, `answer_mode` one/any/all, default buckets correct/incorrect, `mc_correct`/`mc_incorrect`, `mc_ai_feedback`) graded by key with no model, the question listing its choices & `RoomIO.offer_choices` emitting `activity_choices` (ids & texts, never the answer) for chat's buttons (`7-activities.js`). A content-only step's own `next_section_and_step` (a target or conditional list) is where it goes next, else the next step in the file. `n+c`/`n-c` count from a number kept as text & from nothing. `make activity-walk` (`activity_walk.py`) plays every activity with dice, no model: what raised, raw `metadata.x` names a learner would see (`{{metadata.x}}` shows the value), unrendered templates, steps never reached
- `sampling.py`: what a chat ask is sent & may spend, pure (environment & arguments only; app.py imports its names): `chat_sampling`, `thinking_budget`, `answer_tokens`, `answer_room`, `stream_retries`, `_env_int`/`_env_float`, & the prompt sizers `prompt_chars` & `shrink_history`. What reads a model's learned context (`CONTEXT_WINDOWS`, which tests replace on `app`: `fit_max_tokens`, `room_from_refusal`, `fade_to_fit`, `open_completion`) stays in app.py
- `followups.py`: follow-up suggestions' pure half (`FOLLOWUP_PROMPT`, `followups_enabled`, `parse_followups`); app.py's `suggest_followups` asks the model & emits
- `images.py`: images' pure half (`IMAGE_MODELS`, `is_image_model`, `image_request`, `extract_base64_from_img_tag`, `extract_external_image_url`); app.py's `generate_image` & `build_message_content` ask, fetch & save
- `reply_notes.py`: pure text work on a reply's history (`without_echoed_notes`, `answer_from_notes`)
- Blueprints never `import app` (a server started as `python app.py` runs as `__main__`); shared helpers arrive via `routes.DEPS`, Socket.IO via `current_app.extensions["socketio"]`
- A NEW room's name must match `[a-z0-9][a-z0-9_-]{0,63}` (`routes.rooms.valid_room_name`, what `slugify()` in `static/js/utils.js` makes); `/chat/<junk>` is a 404 & creates nothing, rooms that already exist open whatever they're called
- **Limits per address** (`throttle.py`: `Throttle`, `client_ip`, `over_limit` & `too_many`, a 429 with Retry-After; "count/seconds", 0 = off; all pinned off in `tests/conftest.py`, tested in `tests/integration/test_message_limits.py`): `OPENCOMPLETION_MESSAGE_LIMIT` (60/600) counts every message a model answers (`spends_a_model_call` in app.py: a model picked, a `/btw`, an Edit & resend that asks a model again; `/title new` & `/activity info`); an answer to a room's running activity counts against `OPENCOMPLETION_ACTIVITY_LIMIT` (300/600) instead, since a class plays one from a single address; past it a message is neither stored nor dispatched & that socket alone gets a notice saying how long to wait (a resend: `edit_resend_refused`), while people talking to people (model "None") are never limited. `OPENCOMPLETION_OTP_LIMIT` (5/600) sign-in code emails (`/auth/send-otp`) per asking address, `OPENCOMPLETION_OTP_EMAIL_LIMIT` (3/900) the same per TARGET email whoever asks (`too_many(..., key=email)`; a code goes to ONE address: `routes.accounts.EMAIL`, 254 chars at most, no commas, spaces or angle brackets), `OPENCOMPLETION_OTP_VERIFY_LIMIT` (20/600) tries at `/auth/verify-otp`, `OPENCOMPLETION_ROOM_LIMIT` (30/600) new rooms (`/api/rooms/create`, & a socket `join` or `chat_message` naming a room nobody has), `OPENCOMPLETION_CODE_LIMIT` (30/600, `throttle.CODE_THROTTLE`) runs through `POST /api/code/execute`, a model's own `run_code` calls (counted against the address that asked for its reply, `ToolContext.address`; past it the model reads the refusal) & the model calls beside them (`/api/fix-code`, `/api/generate-artifact-name`: `code` & `stderr` 60k chars each at most, a generic error), `OPENCOMPLETION_SPEECH_LIMIT` (60/600) read-aloud requests (`/speech/audio`: only `model`, `input` (60,000 chars at most: Play sends a whole reply), `voice`, `response_format`, `speed` & our service's `sse` go upstream, to an endpoint whose voices listing names that model, else a 400; an upstream's refusal keeps its status, never its words), `OPENCOMPLETION_TITLE_LIMIT` (20/600) Refresh title asks (`/api/rooms/<id>/title` with `generate`; a typed title is never limited), `OPENCOMPLETION_VISION_LIMIT` (60/600) image descriptions (`/vision/describe`: an image's bytes as a base64 data URL no larger than an upload, never an address; our prompt & a listed vision model only; a generic error), `OPENCOMPLETION_SEARCH_LIMIT` (60/600) message searches (`/browse?q=` & old `/search?keywords=`; `search_messages` skips a word under 3 characters & ranks only its 200 newest matching messages)
- Model routing (`app.py`): a model id is pinned to the lowest `MODEL_ENDPOINT_n` listing it (`MODEL_CLIENT_MAP`) & `MODEL_ENDPOINTS` keeps every endpoint serving it, pin first. A pin that fails its health check, or fails while its stream is being opened (`open_with_failover`: connection errors, timeouts & 5xx, never a 4xx), hands over to the next copy of the same model; only with every copy down does `DEFAULT_MODEL`'s rotation answer. `/models` answers at once from the map we have; one older than `ENDPOINT_HEALTH_TTL` is rebuilt in a background greenlet (one at a time; `initialize_model_map` builds aside & swaps in, so nobody reads a half-built map). A `MODEL_n` whose endpoint is down looks for its model (`MODEL_NAME_n`, else what it last listed) on other endpoints first. A stream that breaks while being read carries on (`ReplyStream.carry_on`): asked again, failing over likewise, with what it wrote so far & a note to continue where it stopped, up to `OPENCOMPLETION_STREAM_RETRIES` (2; 0 = off) times a reply; past that, the reply keeps its words & says the stream broke
- **Room chains** (`chain.py`, table `room_event` & `room_checkpoint`, migration `2026110201`): every event in a room (a person's message, each finished tool call's result as the model was handed it, chained before the reply that cites it, the reply naming those tool events, edits, deletes & restores, Edit & resend, forks, attachments, the room's deletion) is one unfirehose-chain-v1 line, hash-linked to the one before, with merkle-v1 checkpoints after each reply; lines carry sha256 digests, never words. An `edit` or `delete` line names its message's author (`username`) & who did it (`by`: the name that socket joined under, `byUserId`: their account when signed in; `acting()` in app.py), since in a public chatroom anyone may change any message. `provenance.py` is uncloseai-cli's code, VENDORED verbatim (never edit; `tests/unit/test_provenance.py` replays the known answers shared with arborist, unfirehose & its Go SDK). A chain is one room's life (`<id>@<created_at>`: SQLite reused ids until migration `2026111201`) & outlives the room, as forensics for abuse. Best effort: a failure to chain logs & never blocks the chat. `GET /api/rooms/<id>/chain.jsonl` & `/chain/proof/<hash>` under the room's access rule (every download names its file through `routes.rooms.download_as`: safe characters in `filename`, the exact name in RFC 6266's `filename*`, since an old room's name may hold anything); `OPENCOMPLETION_CHAIN_MIRROR` (a directory) also appends each line to `opencompletion-<chain>.jsonl` for an outside witness (unfirehose's ingester)
- **Image models** (`generate_image` in app.py): a model whose id matches `OPENCOMPLETION_IMAGE_MODELS` (a regex; default `^(gpt-image|chatgpt-image|dall-e)`) draws instead of chatting: `dispatch_message` sends our message as a prompt to `/images/generations` on the endpoint that lists it, & its image is kept in our blob store & posted as that model's reply. No id is written in our code: an endpoint's `/models` (OpenAI's lists its image models too) fills our picker, so a retired model (dall-e-3 left OpenAI's API 2026-05-12) drops out & its successor shows up by itself. `OPENCOMPLETION_IMAGE_SIZE` (1024x1024) & `OPENCOMPLETION_IMAGE_QUALITY` (unset: the model's default; low/medium/high price an image very differently). GPT image models refuse `response_format`; only a `dall-e*` id is sent it
- **Migrations at startup** (`db_migrate.py`): a deploy is a restart, so `python app.py` (& `init_db.py`, what our container runs first) brings our database up to date before anything reads it: a new one is created & stamped at our newest migration; one stamped behind is copied aside (`<db>.before-<revision>.bak`, SQLite's own backup, mode 600) then migrated; tables with no stamp, or a stamp this code does not know (a database newer than its code), are left alone with a `[WARN]` saying what to do. A migration that fails stops startup, its copy kept. `/version` says what that start did (`migrations`: new, current, migrated, unstamped, unknown, off, or `not run` when we were started some way that skips it; `migration`: the revision). `OPENCOMPLETION_AUTO_MIGRATE=off` skips it; `make upgrade-db` still works by hand. A new migration needs nothing else to ship. **Ids are never reused** (migration `2026111201`): `room`, `message`, `attachment` & `sandbox` are AUTOINCREMENT (`sqlite_autoincrement` in models.py), their sequences seeded past every id the chain ever recorded, deleted rooms' too; `room_event`/`room_checkpoint` are insert-only, `activity_state`/`user_session` ids never leave us
- `SQLALCHEMY_DATABASE_URI` overrides our default `instance/chat.db`. `message.content` is Text (migration `2026112101`: a real column change off SQLite; on SQLite nothing, since it ignores a declared length & altering would rebuild `message` & its id sequence)
- Startup prints, per endpoint, how many models it listed (never their ids: an endpoint may list hundreds) & `Loaded models: <count> (<first five ids>, & N more)` (`loaded_models_line`), then: speech voices, the transcription model, the classifier, then `startup_summary()` (tools & who gets them, chat sampling & budgets, brand, public url, database & its migration); counts & names only, never a key, an email or a database password
- `gevent_asyncio.py`: `wake_executor_jobs()`, called beside `monkey.patch_all()` (app.py, `tests/unit/test_tools.py`). Under gevent's patch, CPython 3.13.12+, 3.14.3+ & 3.15 never wake an event loop when an executor job ends, so a loop's second `asyncio.to_thread` / `run_in_executor` hung (our crawler's tests on CI; gevent 26.9.0 has no fix). `tests/unit/test_gevent_asyncio.py` proves the fix & that this Python still needs it: when its last test fails, the module can go
- `SECRET_KEY` signs session cookies; unset, `auth.load_secret_key` keeps a random one in `instance/secret_key` (never a built-in default). An https `OPENCOMPLETION_PUBLIC_URL` marks a real deployment (`auth.served_over_https`): session cookies are then `Secure` (`OPENCOMPLETION_COOKIE_SECURE` on/off overrides) & a sign-in code no mail server took is never printed to our log, the ask fails instead (`OPENCOMPLETION_OTP_CONSOLE` on/off overrides; a dev server still prints it). No request body past 32 MB (or twice our upload limit) is read: a 413 (`MAX_CONTENT_LENGTH`). Fetched vision images stop at our upload limit & their in-memory cache keeps its 32 newest (`Recent`)
- CI on `main` tests CPython 3.11, 3.12, 3.13, 3.14 & 3.15 (every release still receiving fixes); feature branches & pull requests run every test once, on 3.12 (what our dev venv runs), inside the coverage jobs, plus lint & YAML validation: no plain test job & no Docker build off `main`. Lint & coverage run on 3.12; job `all-green` is one status for a whole run

### Frontend Structure
- **Read `docs/STYLEGUIDE.md` before touching a template or style.css**; `/styleguide` renders every component
- Every page shares one app shell like ChatGPT's: `templates/layout.html` + `_app_sidebar.html` (our name on top, every link, Your rooms (5, then Show all) & Public rooms, the person pinned at the bottom; a drawer on phones). Home & chat (`base.html`) extend it too; there is no site header
- **Asks & toasts** (`static/js/utils.js`): never a browser's `confirm`, `prompt` or `alert` (they block the page & can't be styled; `tests/functional/test_dialogs_ui.py` fails on one). `askConfirm({title, body, confirmLabel, danger})` resolves true or false & `askText({title, label, value, confirmLabel})` what was typed or null, both one modal `<dialog class="ask-dialog">` (Cancel, Escape & its backdrop mean no; `danger` starts focus on Cancel; focus returns to its opener), so a handler that asks is `async`. `toast(message, {error})` is a line atop our page that leaves by itself (`role="status"`, 5s; an error `role="alert"`, 8s). A browser test answers an ask by clicking `dialog.ask-dialog [data-ask="confirm"]` (or `cancel`) & reads `.toast-text`
- **Activities gallery** (`/activities`, `templates/activities.html` + `_activity_card.html`, `static/js/activities.js`; in our sidebar beside Rooms): a card per activity (title, one line, a kind badge: game, lesson or tool), filtered by kind (`.segmented`, `?kind=`) & by words as you type. **Play** makes a new public chatroom (`createChatRoom` in `utils.js`, home's own), titles it after the activity & hands chat `/activity <path>` as its pending message (`keepPendingMessage`), the same command the chooser in a room's controls sends. Cards come from `routes.rooms.activity_cards()`, the one lister behind `/api/activities` too (`activities`: paths, `details`: cards): `activity_gallery.py` reads each YAML's own `title` / `description` / `kind`, else derives them (heading or file name; opening prose cut at a sentence, ~140 chars; game = any script or `metadata_random`, else lesson; tool only when a YAML says so), cached by mtime, no model asked & no script ever run; a file it cannot read keeps its name only & offers no Play. Listed from research/*.yaml, the only place an activity loads from (`activity.get_activity_content`: its scripts run on our server, so never a bucket or a path outside research/); our page shows files named `activity*`. `--local-activities` is still accepted & does nothing
- Our home `/` is an empty chat (`templates/home.html` + `static/js/home.js`); the first message creates a room (**Solo** = only you, `is_private` underneath, needs sign in; Chatroom is public & multiplayer; say Solo, never Private, in copy) & `sessionStorage.pendingMessage` hands it to chat, which sends it on the server's `joined` event; an unsent message outlives a refresh as a draft per place (`keepDraft` in `composer.js`: localStorage `draft:home` & `draft:room:<name>`, never crossing; cleared when sent). While `/models` is on its way a model picker says "Loading models…" & Send waits for it (`modelsLoading` in `utils.js`, home & chat). A guest's rooms live in their browser (`recentChats`, localStorage: name, title, id & whether anyone may retitle it), which feeds their sidebar & our Rooms page's Yours
- A room is titled after its first model reply (`title_untitled_room` in app.py), and an untitled one holding a conversation is titled in the background when someone opens it, so Your rooms (5, then Show all) & Public rooms show titles, not slugs; `source vars.sh && make backfill-titles` titles every untitled room at once
- **Fork** sits on every model reply (`addForkButton` in `5-messages.js`; history messages carry `from_model`): `POST /api/messages/<id>/fork` makes a new chat holding every message up to & including that reply (solo when signed in, a public chatroom for a guest); `/api/rooms/<id>/fork` still forks a whole room. Both share `fork_conversation()` in `routes/rooms.py` & `throttle.py`'s per-address limit, `OPENCOMPLETION_FORK_LIMIT` ("count/seconds", default 10/600, 0 = off); 429 with Retry-After past it. Clients are told apart by the address our proxy appended to X-Forwarded-For, `OPENCOMPLETION_PROXY_HOPS` proxies from the right (default 1 for Caddy; 0 = socket address, when nothing fronts us)
- **Edit & resend** (`edit_and_resend` socket event, `resendEditedMessage` in `5-messages.js`): on a person's message, **Save & resend** (its author only: the name this socket joined under) hides that message & everything after it for everyone in the room, posts the edit & has the models that answered it answer again (else the picked model). Nothing is deleted: hidden rows carry `superseded_by_id` (the revision) & the revision carries `revision_of_id`, so every branch stays a conversation tree. **Versions**: a revision carries a `‹ 2/2 ›` pager (`addVersionPager`; payloads carry `versions`, `Message.version_count`) that opens each earlier version with what was said after it under the message, read only & on that screen alone (`GET /api/messages/<id>/versions`, the room's access rule; `Message.earlier_versions`); nothing a model reads changes. An open version's **Continue from here** makes a new chat, as Fork does (solo when signed in, a public chatroom for a guest; Fork's limit, copying & chain event, plus `revisionId` & `version`), holding the conversation as it stood in that version: `POST /api/messages/<id>/versions/<n>/fork` (n from 1, the oldest), rows by `Message.as_it_stood` (with R the revision that hid that version's branch: id < R & `superseded_by_id` None or >= R); its source room never changes. Read a room through `Message.visible(room_id)`, never `Message.query.filter_by(room_id=...)`. Refused while a reply streams. Migration `2026102702`
- **Undo** for deletes (`delete_message` / `restore_message` socket events, `deletedLine` in `5-messages.js`): in a public chatroom anyone may delete any message, so Delete keeps its row, marked `deleted_at` (epoch seconds) & `deleted_by` (the joined name), & `Message.visible()` skips it: history, what a model reads, downloads, forks, search, titles & stats treat it as gone. Everyone in the room sees one quiet line in its place (who wrote it, who deleted it, **Restore**; `message_deleted` carries a marker, never its words) & anyone who may open the room may restore it (`message_restored`, placed by id: `placeById`). Someone joining later gets those lines for messages deleted in the last `OPENCOMPLETION_DELETED_RETENTION_HOURS` (24; 0 = never shown or restorable; rows are kept either way). Our chain records `delete` then `restore` (its `contentSha256`, `by`, `byUserId`), & `chain._latest` counts a restored message again, so `chain.verify` & download proofs hold. ### Classifier model: a second kind of model (gated enhancement)

`classifier.py` talks to a DECISION endpoint: one `state`, typed questions
(`choice` over the buckets, `noul` yes/no, `score` over ordered levels),
answers with a probability per label & nothing to parse. Same shape & env
vocabulary as `uncloseai-cli/classifier.py` & `unhomeschool/classifier.py`,
vendor-agnostic on purpose (wire shape today: TypeSafe System One, models
`jev-latest` / `jev-preview`, or a LiteLLM `/typesafe` proxy)
(its environment variables: `vars.sh.sample`)

Sites: `activity.categorize_response` & `research/guarded_ai.py`'s copy
(choice over the step's buckets; `Question:` + `Response:` as state, the
step's `tokens_for_ai` as instructions) & Jev Reasoner in Battleship
(`jev_hunter.py`, below). Feedback PROSE stays on the chat model; a decision
model writes none. `classifier_model` / `feedback_model` in a YAML keep
naming CHAT models; the classifier model is discovered from the environment
only.

**Fail-open, never a floor.** Any vendor error, timeout or unanswered
question runs the chat path exactly as before & leaves `classifier_error`
on `activity.last_readout()`, so a vendor failing on every call never looks
like one that is off. Readouts carry `source: chat|classifier` plus the
vendor's `confidence`, `instance` & `model`. `tests/conftest.py` pins the
knob off so a developer's endpoint never turns a unit test into a vendor
call; `tests/unit/test_classifier.py` exercises it with `urlopen` replaced.
`make classifier-check` is the smoke test. Secret hygiene: the key is read
inside the request builder only, never an argument, a result, an error or a
log line.

### Jev Reasoner: a probability grid read by a decision model (Battleship)

`research/activity29-battleship.yaml` offers five enemy admirals: Random,
Hunter, Super Human Hunter (heuristic grid), LLM Reasoner (grid + a chat
model reasoning in prose, formerly "Hermes Reasoner") & **Jev Reasoner**
(`jev_hunter.py`). Jev Reasoner recomputes an EXACT placement-density grid
every turn (every placement of every ship still afloat that avoids misses &
sunk cells; while a hit is live only placements explaining it count,
weighted by how many they cover), offers the top six cells to a classifier
model as ONE `choice` question (the ASCII board & per-cell evidence as
state & criteria, plus a `choice` on the wounded ship's orientation), fuses
jev's distribution with the grid (grid 0.6, jev 0.4, each on its own max
scale, so jev overturns a near-tie & never a landslide), & fires the
maximum. No classifier:
the grid alone decides & the readout says so (`jev_read.source: grid`).
The activity draws the fused grid as a third heatmap panel & the Shot
Report narrates jev's call. **Fleet Setup** (step `setup`) lets the player
take a random fleet or place each ship (step `place`: two tiles per ship,
validated by `battleship_modes.place_ship`; "random" fills the rest); the
computer's fleet is always random. `python3 jev_hunter.py [games] [seed]`
self-plays the grid alone (mean ~44 shots per fleet, 2026-09-18);
`tests/unit/test_jev_hunter.py` covers the grid, the wire & the fail-open.

## Style

- Prefer "our" for shared things; "a" when something is one of many; avoid "the" — it implies fixed, singular ownership. Most teams and systems are fluid and ever-changing, like water.
- **Never use "AI" — always say "machine learning."** We grow machine learning, not "AI." This term is forbidden in all permacomputer discourse, marketing, & documentation.
